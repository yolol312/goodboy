# 리팩토링

기능 변화 없이 코드 구조만 개선하는 워크플로우입니다. 변경 전후 동작 동일성 보장이 핵심입니다.

## 워크플로우

1. **필수 정보 수집**: UserPromptSubmit hook이 누락 정보를 자동 감지합니다. 누락이 있으면 `AskUserQuestion`으로 묶어서 묻고, 각 질문에 "확인 필요" 옵션을 자동 포함시킵니다.

2. **추론 가시화** ⚠️ 필수: 작업 시작 전에 다음 형식으로 `## 추론` 섹션을 출력하세요. 이게 없으면 PreToolUse hook이 편집을 차단합니다.

   ```markdown
   ## 추론

   ### 사실 (검증됨)
   - 실제 Read한 코드/문서로 확인된 것만

   ### 추론 (사실에서 도출)
   - 검증 가능한 논리적 추론

   ### 가정 (정보 부족)
   - 사용자가 "확인 필요"라 답한 항목들 — 어떻게 가정하고 진행할지

   ### 추측 ⚠️ (근거 약함)
   - 검증 없이 채운 부분. 리뷰가 우선 검증함
   ```

3. **카테고리별 세부 단계** — 아래 섹션 참조.

4. **자동 검증**: Edit/Write 후 PostToolUse hook이 타입체크/린트/테스트 자동 실행. 실패 결과는 컨텍스트로 주입되니 확인 후 수정.

5. **테스트** ⚠️ 필수: 코드를 고쳤으면 `test-changes` 서브에이전트를 호출하세요. Stop hook의 층1 테스트 게이트가 테스트 결과 파일이 없으면 종료를 차단합니다.

   ```
   Agent(test-changes, "다음 변경을 테스트: <변경 파일> / 카테고리: <이 워크플로우>")
   ```

   컨테이너로 의존 프로세스를 띄우고 단위·통합·E2E를 작성·실행하며, red-green과 뮤테이션 프로브로 "통과하지만 아무것도 검증하지 않는 테스트"를 배제합니다. 테스트 파일은 repo에 남습니다.

6. **리뷰** ⚠️ 필수: 테스트가 통과한 뒤 `review-changes` 를 **축별로 병렬 호출**하세요. Stop hook이 리뷰 결과 파일이 없으면 종료를 차단합니다.

   먼저 띄울 축을 결정적으로 확인합니다:

   ```bash
   bun ${CLAUDE_PLUGIN_ROOT}/lib/cli.ts review-axes <변경 파일...>
   ```

   그 다음 **한 메시지에서 여러 Agent 호출을 동시에** 보냅니다 — 그래야 실제로 병렬입니다.

   ```
   Agent(review-changes, "축: hallucination / 파일: <변경 파일> / 카테고리: <이 워크플로우>")
   Agent(review-changes, "축: refactoring  / 파일: <변경 파일> / ...")
   Agent(review-changes, "축: security     / 파일: <변경 파일> / ...")
   Agent(review-changes, "축: performance  / 파일: <변경 파일> / ...")
   ```

   `hallucination` 축은 변경 내용과 무관하게 **항상** 포함합니다. 나머지는 `review-axes` 출력이 알려줍니다. 각 축은 자기 차원만 `dimensions_checked` 에 채우고, Stop hook이 합집합으로 커버리지를 판정합니다.


## 카테고리별 세부 단계

1. 변경 전 동작 확인 (관련 테스트 실행 — 모두 통과 상태에서 출발)
2. `## 추론`에 변경 전후 동작 동일성 보장 방법 분류 (사실=실제 통과한 테스트 / 추론=호출 그래프 / 가정=불명 / 추측=환각 위험)
3. 작은 단위로 리팩토링 + 즉시 검증 반복 (한 번에 한 리팩토링 패턴만)
4. 모든 기존 테스트 통과 확인 (새 테스트 추가는 가능, 기존 테스트의 단언을 임의로 약화하지 말 것)
5. 리뷰 호출

## 설계 시 반영할 품질 차원 (해당 시)

⚠️ **shift-left**: 전체 체크리스트는 `/add-feature`의 "설계 시 반영할 품질 차원" 섹션 참조. refactor에서 특히 챙길 것:

- **동작 보존(preserve behavior)**: 리팩토링은 동작을 바꾸지 않는다. 기존 테스트가 모두 통과해야 하고(실제 실행), 단언을 약화하거나 삭제하지 말 것. 리뷰는 기존 테스트 전부 통과를 실행으로 확인함.
- **성능 회귀 금지(`performance`)**: 구조 개선이 핫/요청 경로에 동기 IO나 O(n) 증가를 새로 들이지 않는지 확인. 트레이드오프가 있으면 `## 추론`에 명시.
- 리팩토링이 위 add-feature 트리거(프론트엔드/HTTP 서버/외부 입력 파싱)에 닿으면, 그 차원도 기존 수준 이상으로 유지(접근성·헤더·에러 핸들러를 리팩토링하며 떨어뜨리지 말 것).

## 위험도

이 카테고리의 기본 위험도: **중간(medium)**

- 단순(simple): 자동 진행 게이트 — 추론 가시화만 필수
- 중간(medium): 추측 카테고리에 항목이 있으면 사용자 확인 게이트
- 위험(risky): 항상 사용자 승인 마커(`.claude/.goodboy-risk-approved.txt`)가 있어야 편집 가능. 사용자에게 "진행 승인" 명시 요청.

`--risk <level>` 인자로 override 가능. 예: `/refactor --risk risky <설명>`

## 주의사항

- "확인 필요" 답변은 정당한 입력입니다. 모델이 거짓 답변하지 말고 그대로 가정 단계에서 명시하세요.
- `## 추론 > 가정` 섹션에 "사용자가 X에 대해 모른다 → ~로 가정"이라고 명시.
- 추측이 많을수록 리뷰가 엄격해집니다. 가능하면 사실/추론 비중을 높이세요(Read로 검증).
- 기존 테스트 커버리지가 부족하다고 답이 온 경우, 리팩토링 전에 특성화 테스트(characterization test) 추가를 먼저 제안하세요.
- 리팩토링과 기능 변경을 같은 커밋/PR에 섞지 마세요. 동작 변경이 필요하면 `/fix-bug` 또는 `/add-feature`로 분리.
